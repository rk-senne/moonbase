# Design: TUI Refactor

## Approach

Five coordinated changes, each grounded in a principle from the research library, each
independently shippable. The order is deliberate: the cheapest, highest-leverage change
(KeyMap) goes first because it also unlocks the help-generation and footer work; the
riskiest change (god-struct decomposition) goes last, after the safety net of golden
tests is in place.

The overarching constraint is **behaviour preservation**. Uncle Bob's "do no harm to
function, do no harm to structure" cuts both ways here: we improve structure while
proving — via the existing 91.2%-coverage `Update` tests plus new golden tests — that
function is unchanged.

## Design Decisions

### D-1: Centralised `KeyMap` with `bubbles/key` — satisfies FR-1, FR-4

**Principle: DRY (The Pragmatic Programmer).** "Every piece of knowledge must have a
single, unambiguous, authoritative representation within a system." Today the knowledge
"pressing `n` advances the pipeline" is represented twice — once as `case "n":` in
`update_dashboard.go`, and once as prose in `views_help.go` — with nothing keeping them
in sync. That is a textbook DRY violation, and the help view is already at risk of
drift.

**Design.** Introduce `internal/tui/keys.go`:

```go
type KeyMap struct {
    Up, Down       key.Binding
    Enter, Back    key.Binding
    NewMission     key.Binding
    NextPhase      key.Binding
    RetryPhase     key.Binding
    SkipPhase      key.Binding
    Search         key.Binding
    CycleTheme     key.Binding
    OpenComms      key.Binding
    // … one field per logical action
}

func DefaultKeyMap() KeyMap {
    return KeyMap{
        NextPhase: key.NewBinding(
            key.WithKeys("n"),
            key.WithHelp("n", "next phase"),
        ),
        // …
    }
}

// ShortHelp / FullHelp implement help.KeyMap so bubbles/help can render both.
func (k KeyMap) ShortHelp() []key.Binding { … }
func (k KeyMap) FullHelp() [][]key.Binding { … }
```

Key handlers change from `case "n":` to:

```go
switch {
case key.Matches(msg, a.keys.NextPhase):
    return a.handlePipelineAdvance()
case key.Matches(msg, a.keys.RetryPhase):
    return a.handlePipelineRetry()
}
```

The help view and the per-view footer are both generated by `bubbles/help` from the
`KeyMap`, so AC-1.3 (help cannot diverge) and FR-4 (contextual footer) fall out for
free.

**Alternatives considered:**
- *Keep string literals, hand-maintain help (status quo).* Rejected — the drift risk is
  the whole problem; this is the DRY violation we are fixing.
- *Custom key-registry type instead of `bubbles/key`.* Rejected — `bubbles/key` is
  already a transitive dependency, is the idiomatic Bubbletea solution, and co-locates
  keys with help text (`key.WithHelp`), which is exactly the single-source-of-truth we
  want. Building our own would violate "don't reinvent what the framework gives you."

**Why first:** It is mechanical, low-risk, touches ~53 well-understood sites, and every
other UX improvement (footer, generated help) depends on it.

### D-2: Contextual help footer via `bubbles/help` — satisfies FR-4

**Principle: Clarity (terminal UX research) + feedback (GUI design principles).** Good
terminal UX surfaces "what can I do right now?" without forcing the user to open a
manual. Because the `KeyMap` from D-1 already carries help text, the footer is a thin
projection: each view exposes the subset of bindings valid in that view, and
`help.Model` renders them.

**Design.** Each view (or sub-model, after D-5) returns a `[]key.Binding` describing its
active keys. `App` holds a `help.Model` and renders `help.View(currentViewKeys)` in the
status bar. `?` toggles `help.ShowAll` for the long form (replacing the hand-written
`renderHelp`).

**Alternative considered:** *Static footer string per view.* Rejected — reintroduces the
exact DRY/drift problem D-1 removes.

### D-3: Themes as immutable values + registry — satisfies FR-2

**Principle: No global mutable state / Orthogonality (Clean Code; The Pragmatic
Programmer).** `cycleTheme()` mutating package-level `var ColorActive …` means the theme
is ambient global state: two `App` values (e.g. in tests) can't hold different themes,
it isn't `-race`-safe, and rendering depends on hidden state. Orthogonality says a
change to "which theme is active" should be local and explicit, not a global
side-effect.

**Principle: Open-Closed Principle (Clean Architecture, ch. 8).** Adding a theme today
means editing the `switch` in `cycleTheme()` — modification. A registry makes it
extension.

**Design.** Define an immutable `Theme` value and a registry:

```go
type Theme struct {
    Name                             string
    Active, Warning, Error, Info     lipgloss.Color
    Brand, Text, Muted, Dim, Bg      lipgloss.Color
}

// Styles derives lipgloss styles from a Theme (pure function of the theme).
type Styles struct { Header, Sidebar, Panel, Active, … lipgloss.Style }
func NewStyles(t Theme) Styles { … }

var themeRegistry = []Theme{moonbaseTheme, treehouseTheme, classifiedTheme, nervTheme}
```

`App` holds `theme Theme` and `styles Styles`. `cycleTheme()` advances an index into
`themeRegistry` and recomputes `styles = NewStyles(theme)` — pure, local, no globals.
Render code reads `a.styles.X` instead of the package-level `Style*` vars.

**On `themeRegistry` being module-level.** The steering says "no global state," which
this honours in spirit: `themeRegistry` is a compile-time constant list that is never
mutated after init (unlike today's `Color*` vars, which are reassigned on every theme
cycle). It is read-only shared data, not mutable global state. Making it a `var` is
idiomatic Go for a fixed lookup table; if themes ever become user-loadable (FC-2) it
would move behind a constructor.

**Alternatives considered:**
- *Keep globals but guard with a mutex.* Rejected — mutex on render-hot globals is both
  a performance and a design smell; it treats the symptom (races) not the cause (shared
  mutable state).
- *Full theme-file loading from disk now.* Rejected — YAGNI. The registry leaves that
  door open (FC-2) without building it.

**Migration note:** `styles.go`'s package-level vars are the most widely-referenced
symbols in the package. To keep D-3 shippable, introduce `Styles` first and migrate
render sites incrementally, deleting the globals only once no references remain.

### D-4: Bounded golden-file tests + Humble Object — satisfies FR-5, protects NFR-1/2

**Principle: The Humble Object pattern (Clean Architecture, ch. 23).** "The View is the
humble object that is hard to test… The Presenter is the testable object." In Bubbletea
terms: `View()` is humble (pure formatting, volatile), `Update()` holds the testable
logic. Moonbase already follows this — its ~91% coverage is on `Update`. We keep that.

**Principle: Keep GUI tests minimal (The Clean Coder).** "GUIs are volatile. Test suites
that operate through the GUI must be fragile… Keep the GUI tests to a minimum." So
golden tests are a **thin safety net for the refactor**, not a new testing strategy:
primary views only (dashboard, pipeline, dossier), fixed size and state.

**Design.** `internal/tui/golden_test.go` renders each primary view with deterministic
state at a fixed 100×30 and compares to `testdata/*.golden`. A `-update` flag
regenerates them. These exist mainly to prove D-5 (decomposition) changed no pixels; once
stable they rarely change.

**Alternative considered:** *Snapshot every view + comprehensive golden coverage.*
Rejected per Clean Coder — volatile, high-maintenance, would rot. Behavioural testing
stays on `Update`.

### D-5: Decompose `App` into cohesive sub-models — satisfies FR-3

**Principle: Single Responsibility / Common Closure (Clean Architecture, ch. 7 & 13).**
"Gather together those things that change at the same times and for the same reasons.
Separate those things that change at different times or for different reasons." The 57
fields of `App` change for many reasons: file-browser fields change when browsing logic
changes, comms fields when chat changes, terminal fields when the embedded shell
changes. These are different actors → they belong in different types.

**Principle: Information hiding / deep modules (A Philosophy of Software Design).** Each
sub-model should expose a small interface (`Update`, `View`, focus) and hide its fields,
so `App`'s key handlers stop reaching into per-view internals.

**Design.** Extract sub-models incrementally, using the already-partially-extracted
`CommsState`, `DocsState`, `ProjectsState`, and `FileBrowser` as the template:

```go
type App struct {
    // Orchestration + shared state only (~≤15 fields):
    view        View
    keys        KeyMap
    theme       Theme
    styles      Styles
    help        help.Model
    registry    *agents.Registry
    width, height int
    // Sub-models own their view state:
    dashboard   DashboardModel
    pipeline    PipelineModel
    comms       *CommsState
    files       *FileBrowser
    terminal    TerminalModel
    // … shared services (backend, projectCtx) stay at top level
}
```

Each sub-model owns its fields and exposes:

```go
func (m DashboardModel) Update(msg tea.Msg, ctx AppContext) (DashboardModel, tea.Cmd)
func (m DashboardModel) View(styles Styles) string
```

**Note — sub-models are deliberately NOT `tea.Model` implementations.** They return
their own concrete type (`DashboardModel`, not `tea.Model`) so `App` keeps value
semantics and avoids interface-boxing churn on v1. This is intentional: it keeps them
trivially testable as plain values and is a natural stepping stone to full nested
`tea.Model`s under a future v2 migration (FC-1).

`App.Update` routes to the active sub-model; `App.View` composes sub-model views with
`lipgloss.JoinVertical`. Shared services the sub-models need (registry, backend, sizes)
are passed in via a small read-only `AppContext`, not by handing over the whole `App`
(Interface Segregation — depend only on what you use).

**`AppContext` is bounded (guards against a second god-object).** It is a read-only
struct with a fixed, small field set — the sub-models depend only on what they use:

```go
type AppContext struct {
    Registry   *agents.Registry   // read-only lookups
    Backend    backend.Backend    // active backend (not mutated by sub-models)
    ProjectCtx *discovery.ProjectContext
    Styles     Styles             // derived from the active theme
    Keys       KeyMap             // for key.Matches + footer
    Width      int
    Height     int
}
```

Sub-models MUST NOT mutate anything reachable through `AppContext` (it carries pointers
to shared services for reading only). If `AppContext` ever needs to grow past ~8 fields,
that is a signal to split it by consumer (ISP) rather than widen it.

**Alternatives considered:**
- *One big struct, just group fields with comments.* Rejected — cosmetic; the type still
  changes for every reason and stays untestable in isolation.
- *Full Elm-style nested `tea.Model` sub-programs.* Rejected for now — heavier than
  needed on v1 and a larger blast radius. The chosen "struct-with-Update-method"
  sub-models capture 90% of the benefit at a fraction of the risk, and are a natural
  stepping stone to full nesting under a future v2 migration (FC-1).

**Why last & phased:** highest blast radius. It runs only after D-1..D-4 are merged and
the golden tests (D-4) can prove no visual regression. Each sub-model extraction is its
own task with its own green build.

### D-6: Colour-profile degradation guard — supports FR-2, FC-5

**Principle: Robustness / "be liberal in what you accept" (Pragmatic Programmer).**
Lipgloss already downsamples truecolor to the terminal's profile, but we add an explicit
guard: honour `NO_COLOR`, and ensure status is never conveyed by colour alone (the
weight-first palette already helps). This is a small, defensive addition folded into the
theme work (D-3), not a separate subsystem.

## Component / Data View (C4 "component" level)

```
                 ┌──────────────────────────────────────────┐
                 │                  App                      │
                 │  (orchestration, routing, shared state)   │
                 │                                           │
                 │  keys KeyMap   theme Theme  styles Styles │
                 │  help help.Model   view View             │
                 └───────────────┬───────────────────────────┘
        routes msg to active     │ passes read-only AppContext + Styles
        ┌────────────┬───────────┼───────────┬────────────┐
        ▼            ▼           ▼            ▼            ▼
  DashboardModel PipelineModel CommsState FileBrowser TerminalModel
   (own fields,   (own fields,  (exists)   (exists)    (own fields,
    Update/View)   Update/View)                          Update/View)

  keys.go ──────────► DefaultKeyMap() is the single source for
                      key handling (key.Matches) AND help (bubbles/help)

  theme.go ─────────► themeRegistry []Theme  ── NewStyles(Theme) ─► Styles
```

Dependency direction: sub-models depend on `KeyMap`/`Styles`/`AppContext` (stable,
abstract-ish values); `App` depends on sub-models. Nothing depends on package-level
mutable globals after the refactor (they are deleted).

## Edge Cases

| Scenario | Handling |
|----------|----------|
| Same physical key means different things in different views (e.g. `s` = skip phase vs. something in comms) | `KeyMap` bindings are matched within the active view's handler; per-view footer only lists that view's bindings (AC-4.3) |
| Terminal smaller than content | Existing width/height handling preserved; footer truncates via `bubbles/help` width; documented as FC-4 for deeper work |
| `NO_COLOR` set | Theme returns an uncoloured/degraded palette (D-6) |
| Golden test on a machine with different default profile | Tests pin width/height and render with a fixed colour profile so output is deterministic |
| Theme cycled mid-pipeline-run | Pure value swap + recompute styles; no effect on pipeline state (orthogonality) |
| A sub-model needs a shared service (backend, registry) | Passed via read-only `AppContext`; sub-model does not mutate shared services |

## Test Alignment

Per `.kiro/steering/test-alignment.md`:

| Change | Required Test | Validates |
|--------|--------------|-----------|
| `KeyMap` + `key.Matches` migration (D-1) | Update tests (existing, adapted) send `tea.KeyMsg{Runes:[]rune("n")}` and assert the same behaviour as before | AC-1.2, NFR-1.1 |
| Help generation (D-1/D-2) | Test that every `KeyMap` binding with help text appears in `FullHelp()` output | AC-1.3 |
| No literals remain (D-1) | A meta-test / grep gate asserting zero `case "…":` keypress branches | AC-1.4 |
| `Theme`/`Styles` (D-3) | Unit test: `NewStyles(theme)` is pure (same input → equal output); cycling advances registry and wraps | AC-2.1, AC-2.3 |
| Theme is pure value transform (D-3) | `TestCycleTheme_PureValueTransform` — cycling returns a new model with a different theme and touches no package-level state | AC-2.5 |
| Theme race (D-3) | `go test -race` over a render loop cycling themes | AC-2.4 |
| Sub-models (D-5) | Each sub-model gets direct `Update` tests (happy path + key handling) in isolation | AC-3.2, NFR-2.1 |
| Golden (D-4) | Golden tests for dashboard/pipeline/dossier at fixed size | AC-5.1, protects NFR-1 |
| Coverage guard | `go test ./internal/tui/ -cover` ≥ 91.2% | NFR-2.1 |

## Risks & Rollback

| Risk | Likelihood | Mitigation | Rollback |
|------|-----------|------------|----------|
| Behaviour drift during key migration | Medium | Existing `Update` tests are the safety net; migrate one file at a time | Revert the single file's commit |
| Golden tests flaky across environments | Low-Med | Pin size + colour profile; document `-update` | Delete golden test; keep `Update` tests |
| God-struct decomposition breaks message routing | Medium | Do it last, per-sub-model, behind golden tests; each extraction is its own green build | Revert the sub-model's commit; `App` still compiles with remaining fields |
| Scope creep into v2 migration | Medium | NFR-4 fences it out explicitly; recorded as FC-1 | n/a |

Every phase leaves the tree building and green (NFR-5), so rollback is always "revert the
last phase's commits."

## Decision Record

- **Stay on Bubbletea v1.** Rationale: v2 is a breaking API change (`View() tea.View`,
  `tea.KeyPressMsg`) and mixing it into a structural refactor multiplies blast radius.
  This spec makes v2 *cheaper later* by centralising keys and decomposing state.
- **`bubbles/key` + `bubbles/help` over a custom solution.** Idiomatic, already a
  transitive dep, co-locates keys and help (the DRY win).
- **Struct-with-Update sub-models over full nested `tea.Model`s.** Captures the SRP/CCP
  benefit at lower risk on v1; natural stepping stone to full nesting under v2.
- **Golden tests deliberately bounded.** Humble Object + Clean Coder: GUI tests are
  fragile, so they stay a thin refactor safety net, not the primary strategy.
